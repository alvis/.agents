# Confirm review patterns

Read after area validation and before reconciling the work-root `review.md`. Only the main agent writes state or asks the user; nested reviewers write their assigned temporary reports and return summaries. Follow Essential's state lease, append-first journal, approval-binding, and output-size contracts. Use [confirmation.md](templates/confirmation.md) for the canonical section; neither global state nor HTML is another home for answers.

## Persist and group

1. Read the previous `review.md` before replacing its derived roll-up. Collect every outstanding finding across all existing validated areas, including unchanged areas in a partial rerun. Group by evidenced shared cause or corrective action, not severity, area, filename, or proximity. Unrelated defects remain separate even when their category matches. Assign each finding to one pattern; a singleton is valid.
2. Keep each matching pattern's `PAT-001`-style ID stable and allocate the next unused ordinal for a new pattern. Record linked member finding IDs, a concise trigger/impact/correction explanation, and one short, self-contained question asking whether that behavior is an issue. Save the area reports and the pattern section with blank `Answer: ` fields before asking about presentation. If writes fail, report the persistence blocker without presenting unsaved findings or soliciting answers.
3. Bind every pattern to its reviewed immutable SHA and exact evidence inputs. For uncommitted changes, include content hashes. Compare member IDs, the claim/question, relevant source content, contracts, and verification evidence on rerun. Preserve a response when those inputs still support the same scope; a new overall commit SHA or shifted line number alone does not invalidate unchanged evidence. Record the comparison to the new revision rather than pretending the old response approved it. Material change, uncertain equivalence, splits, or merges marks affected responses stale: retain original answers and bindings as history, clear the current `Answer: `, and ask only the affected patterns again. Never transfer confirmation to new members silently.
4. Retain response history for patterns whose findings close or disappear, marking them inactive and excluding them from current confirmation counts and issue candidates. A clean review needs no presentation choice or question. Finding counts and review verdicts continue to derive from area dispositions, not pattern counts or user agreement.

## Present and reconcile

For an interactive review with outstanding patterns, ask whether the user wants the pattern summary inline in chat or an interactive HTML study through `essential:discover`. Honor an already selected preference. Both choices show the same pattern IDs, member links, evidence, explanation, and one question per unresolved pattern. The saved report is always available for direct answers.

- **Inline:** present concise pattern summaries with their questions; accept report edits or chat answers identified by pattern. Do not repeat questions for individual locations or reopen unchanged confirmed/rejected answers.
- **HTML:** invoke `essential:discover` with the persisted review as input, the same work ID, and `--mode=interview` for a guided interview. Load its installed skill contract and let its existing renderer build the board from JSON in a collision-safe OS temporary directory; do not hand-write HTML or change discover. Cover all active patterns and evidence links, showing answered patterns as context without asking again. Collect responses and annotations through its one generated reply prompt. Untouched defaults are suggestions. Ask the user to return that prompt, then reconcile its explicit responses into `review.md` before discarding the temporary surface. If discover is unavailable, report that limitation and offer inline/report confirmation.
- **Non-interactive:** persist pending pattern questions and return the existing verdict/exit behavior; no questions, HTML generation, or GitHub write. A delegated reviewer returns its temporary report path and summary; it never claims canonical state was saved.

Treat `Answer: ` as user input, not a field to fill from a recommendation. Read report edits, chat replies, or the returned HTML prompt and record the user's actual words and provenance. An explicit agreement sets `confirmed`; explicit disagreement sets `rejected` and routes the objection to the owning reviewer for reassessment. Free-form notes, blanks, ambiguous responses, and unreturned HTML interaction do not establish confirmation. For partial agreement or exceptions, record the exact scope; clarify only unresolved scope once per affected pattern. Conflicting responses require reconciliation, not an arbitrary winner. Journal the response before reconciling the report under the main-agent lease. If new evidence changes the claim, apply the freshness rule above.

<IMPORTANT>
Confirmation is agreement that a pattern is a problem. It never marks a finding fixed, grants risk acceptance, clears a review gate, authorizes source changes, or authorizes GitHub writes. Rejection alone never dismisses a finding. Any disposition change still needs the area's existing evidence and authority requirements.
</IMPORTANT>

## Verify remote presence and offer issues

Only currently confirmed, active patterns can become issue candidates. Use read-only remote inspection; local branch names, remote-tracking refs, commit ancestry, and a previously merged PR alone cannot prove the defect remains on today's default branch.

1. Resolve the GitHub host and repository from the target's remote or explicit repository. With authenticated `gh`, inspect `bun` [`gh-repo.ts`](../../../scripts/gh-repo.ts) `view --json nameWithOwner,url,defaultBranchRef`; resolve the returned branch through the GitHub API to its immutable commit SHA. Record repository, branch, SHA, and checked time. If the target is ambiguous, access fails, or the remote is not GitHub, mark eligibility `unverified` with the reason and do not suggest creation.
2. Inspect the relevant source and supporting context at that exact SHA through the GitHub API (`repos/OWNER/REPO/contents/PATH?ref=SHA`) or an existing local Git object (`git show SHA:PATH`). Follow renamed paths where evidence supports the mapping. Trace the reported failure or missing behavior on that remote version; do not execute untrusted reproduction code or switch/edit the user's working tree. Mark `absent` when the reported problem is missing, already fixed, or only local. Missing evidence remains `unverified`.
3. Record supporting paths/behavior and the eligible member finding IDs. A pattern may have both published and unpublished locations: propose only its verified remote subset, once per pattern. If the remote behavior changes the confirmed claim materially, re-confirm the affected pattern before offering an issue. Re-resolve the head before offering; when it moved, repeat the affected inspection against the new SHA.
4. Suggest creating one issue per eligible pattern and offer `coding:issue` in read-only preview intent for repository-template drafting and duplicate lookup. Pass target repository, pattern ID, confirmed scope/provenance, verified remote SHA and source links, trigger/impact/evidence, proposed correction, and any existing issue URL. Do not publish local state paths or unrelated/private review content in issue bodies. Let `coding:issue` own templates, duplicate handling, and metadata; do not invent its command options or duplicate its mechanics. If it is unavailable, retain the verified candidates and report the missing owner without creating issues directly.
5. Request issue creation only after the user authorizes that action, unless existing explicit authorization covers the concrete candidates. Confirmation alone is insufficient. Recheck remote eligibility after a delay or new remote evidence before handing off for creation. Reconcile URLs and read-back outcomes returned by `coding:issue` into the corresponding pattern; reuse existing URLs on rerun rather than offering duplicate creation.
