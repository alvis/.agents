# Action: motion-design

Loaded by `SKILL.md` when the requested action is `motion-design`. Craft a motion video from zero: interview the user until the idea is concrete, lock a storyboard, build it as web animation with [HyperFrames](https://github.com/heygen-com/hyperframes) (optionally mixed with Blender renders), and score it with ElevenLabs music and lyrics fitted to the picture. Most video tools start from a formed brief; this action exists to form it.

## Boundaries

- Use when the user wants a new motion video, title sequence, reel, music video, greeting, explainer, or other animated piece, whether the idea is blank or half-formed.
- Do not use for a specific operation on an existing HyperFrames project (render, lint, diagnose, edit one scene): load the HyperFrames skills directly. Do not use for live-action editing or footage grading.
- External skills are linked, never copied. Read each one from its link, or its installed copy, at the step that needs it. If a needed external skill or CLI is missing, name the install command from its own documentation and ask the user before installing anything.
- The workflow writes no Python. Use the HyperFrames CLI, the ElevenLabs CLI or JavaScript SDK, and Blender's command-line flags; when a step seems to need a helper script, write it in JavaScript or TypeScript.
- Media sourced from the web or generated by a provider gets its rights and provenance recorded through the `track` action; never assume a found image is free to use.

## Inputs and output

- **Required**: the user's request, however vague.
- **Optional**: goal, destination, length, references, supplied media, brand, song, lyrics, and any explicit "just build it" signal.
- **Output**: a HyperFrames project containing `BRIEF.md`, `STORYBOARD.md`, the compositions, the music track, and the rendered video; asset and render entries recorded through `track`.

## Workflow

1. **Read what is already decided.** List which of the direction questions below the request clearly answers. A clear statement skips its question; an inference does not. When the user says "just build it" or "surprise me", answer the remaining questions yourself, state each answer with its reason, and continue.
2. **Ask the direction questions with the harness's standard question tool**, one at a time, two to four options each, recommended option first, free text always allowed. Use plain chat only when the harness has no question tool. Do not open an HTML board for these.
   1. **Goal and message**: what the video should achieve and the one thing a viewer must take away. Offer messages inferred from the request.
   2. **Platform**: where it will be watched. Map the answer to aspect, length, and sound behaviour with [platforms](references/platforms.md).
   3. **References and materials**: the user's photos, logos, footage, or brand files; assets to obtain by web search; videos, images, or styles to mimic. Collect paths and links; search for assets only after the user agrees, and record each found asset's source and licence.
   4. **Format**: suggest three or four formats from the [format catalogue](references/formats.md) that fit answers 1–3, each with a one-line reason.
   5. **Mood**: suggest three or four moods that fit the format and platform, each named with a tempo range and a colour temperature so the choice carries into music and palette.
   6. **Subject**: when a real person, pet, or brand figure is on screen, ask about them before designing anything: appearance and signature features, with photos; personality and catchphrases; places and eras of their life; the people around them; real anecdotes and in-jokes. Ask follow-ups until each story can be told from facts the user gave; never invent an anecdote and present it as real.
3. **Interview on a board.** Run `essential:discover` in `interview` mode and present a guided-interview board as its presentation direction describes, carrying answers 1–6 as confirmed context. The board confirms:
   - **Style directions**: five to eight visually distinct directions from the [visual style catalogue](references/styles.md), so the user compares genuinely different looks rather than variants of one. Draw them from at least three rows that differ in medium (print, drawn, 3D, photographic, typographic). Each is shown as an `embed` block holding a short looping animation demo in that style's palette, type, and motion grammar, with a decision to pick, mix, or reject. Each demo is one self-contained HTML file with inline script and no network request, written next to the board in its temporary directory.
   - **Character styles**: when answer 6 applies, six to eight styles from the [character style catalogue](references/characters.md) spanning high, medium, and low likeness, each drawn as the actual subject from their photos and signature features rather than a generic figure. Let the user pick one, mix two, or ask for adjustments such as build, hair, or clothing, and redraw until they confirm the likeness.
   - **Storybook**: five story concepts, each built on a different device from the [story device catalogue](references/story-devices.md), so the choice is between ideas rather than variations of one; at least one should be unexpected for the occasion. Each concept is a sequence of four to eight key moments with a sketch or still and one line of action, uses only facts the user gave, and marks where the music hook lands.
   - **Sound**: instrumental or vocals, vocal character, language, and how the lyric relates to the message.
   - **Anything else**: an open question for what the earlier sections missed.

   Transfer every answer and annotation back to the discovery ledger before continuing. Repeat a board round only when an answer opens a new material question.
4. **Finalize the storyboard** following the [storyboard template](templates/storyboard.md): the arc, shot list on a bar grid, sync points, style sheet, catchphrases (the hook, tagline, and on-screen lines such as "Stroke of a Pen" or "What are you made of?"), and the music plan. Present it in chat for approval through the question tool; revise until approved. A revision is not an approval.
5. **Set up the project.** Follow the `hyperframes` entry skill: run `npx hyperframes init`, then write `BRIEF.md` in the [HyperFrames brief format](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/references/brief-format.md) with `workflow: general-video`, `flow: companion`, `storyboard: yes` for a picture-first piece, or `workflow: music-to-video` when the user supplied the song. Write the approved storyboard as `STORYBOARD.md` in the [HyperFrames storyboard format](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/references/storyboard-format.md) so HyperFrames asks no intent question again.
6. **Build the picture** through the `hyperframes-core` and `hyperframes-animation` skills, following [build](directions/motion-design/build.md). Use [Blender](directions/motion-design/blender.md) only for shots the storyboard marks as 3D beyond what Three.js in HyperFrames can deliver.
7. **Score it.** Follow [music](directions/motion-design/music.md) to generate the track from the locked bar grid, measure it, and refit the cut to the measured beats and words.
8. **Check and render.** Run `npx hyperframes check --snapshots`, review a snapshot at every sync point, then render with `npx hyperframes render` at the platform's aspect and frame rate. Watch the full render with sound before calling it done.
9. **Record and review.** Register supplied, sourced, and generated assets and the render through the `track` action. Route the user's feedback on the render through the `review` action; each feedback round produces a new render revision.

## Verification

- Every question the request clearly answered was skipped; every answered question appears in the ledger with the user's wording.
- The approved storyboard, `BRIEF.md`, and `STORYBOARD.md` agree on message, platform, aspect, length, and arc.
- Every sync point in the storyboard lands within the [music](directions/motion-design/music.md) tolerance of its measured beat or word in the final render.
- No external skill text was copied into the project or this repository; no Python file was written.
- Every sourced or generated asset has provenance and rights recorded, or is reported as pending.

## Completion

Report the confirmed brief, the chosen style direction, character style, and story concept, the catchphrases, the project path, the render path and its revision, sync-point results, assets still pending rights or hashes, and the next action for the user.
