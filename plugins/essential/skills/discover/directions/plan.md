# Plan mode

Use this mode when the user wants to be interviewed toward an implementation direction or architecture, or when `essential:directions/plan.md#confirm-the-direction-and-architecture` requires a review board. Follow that planning direction for the board's required content, diagrams, confirmation, and blocked-rendering behavior. Each round is one rendered HTML board before execution-plan finalization. When the direction is already understood, make the board concise and ask only for confirmation or material corrections.

1. **Scan conventions before asking anything.** Read, without writing: root `README.md` and `AGENTS.md` or `CLAUDE.md`; `docs/` and its architecture decision record index; `.state/` through the injected state contract — open streams, their `goal.md` specification provenance, `decisions/`, and `state/journal.md`; and the external specification authority, such as a Notion page, when that provenance or the user names one. Record each finding as an `observed` ledger row; it either answers a question outright or becomes the evidence beside one. Never ask what the scan already settled.
2. **Rank and frame the open questions** under [interview](interview.md) steps 1–4; each carries a badged recommendation with its reason. When no material question remains, present the settled proposal and its readiness decision without inventing options.
3. **Show alternatives concretely.** For every question that settles architecture or scope, give each option a short illustrative `code` block, or a `codepair` for two, in the target's language and conventions from step 1: the interface, call site, file layout, or authored-content example the option produces, not working code. Include a scope question when scope is still open, contrasting the smallest sufficient surface with larger options. Picked sketches bound the handoff: surface no picked sketch shows stays out of scope unless a later round adds it.
4. **Render the round.** Author one `guided-interview` board under [presentation](presentation.md) and the [guided interview](presentation/actions/guided-interview.md) direction. Include the planning direction's review material even when no alternatives remain. Round two onward opens with confirmed answers so far as context, never as questions again. Give each round a distinct board `id` so a reader's saved answers never cross rounds.
5. **Close every round with one readiness decision.** After the decision synthesis, the last section holds a `decision` asked as a decision — approve reads "Ready to form the execution plan", change reads "Run another round" — plus a note for what the next round must cover. The board's `reply.template` names the ledger path and carries both outcomes, so the copied prompt is self-directing. Either outcome first reconciles `{{answers}}` and `{{notes}}` into that ledger, then:
   - **Another round** — run `/discover plan` again on the same work to render the next round.
   - **Ready** — check the reply against `essential:directions/plan.md#confirm-the-direction-and-architecture`, then form an execution plan from the reconciled ledger and confirmed direction. Untouched recommendations remain open questions, not defaults; if they affect the proposed direction, render another round.
6. **Prototype only when it is cheaper than asking.** Follow [prototype](prototype.md) and link the artifact from that question's evidence.
7. **Discard each round's temporary board** once its reply is reconciled.

Rounds span sessions, so the ledger always persists. This mode never writes `docs/`, the external specification, or the execution plan itself, and never approves one.

Stop when the user explicitly confirms a ready round with no unresolved material direction, or when no remaining question can change architecture, scope, data contracts, or user-visible behavior — then render a final round whose only question is the readiness decision. Complete with the rounds run, confirmed direction and architecture, deferred or blocking questions with owners, and the prompt that hands off to planning.
