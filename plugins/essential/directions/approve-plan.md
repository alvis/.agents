# Persist an approved plan

The main agent follows this direction when the approval hook or OpenCode adapter identifies an explicit implementation submission or a verified successful plan exit. Hook feedback is a routing signal, not proof that a work stream owns the plan. A subagent returns the signal to its main agent without writing state.

1. Recover the current approved candidate: the nonempty plan embedded in the user submission, the successful plan-exit response, or the immediately preceding plan that the submission refers to. Read a native plan file only when this approval identifies it. Check any supplied content hash against those exact bytes. Never choose the newest file by timestamp, an earlier transcript plan, or another session's plan. Missing content, changed bytes, or ambiguous approval scope must be resolved with the user before saving or implementation. A quoted example, negation, generic “yes,” or unapproved tool proposal is not authority.
2. Follow [establish-work-stream.md](establish-work-stream.md), including charter ownership and intent checks, then [the state lifecycle](../references/state.md). Run Essential's resolver from the target repository; select the matching work contextually and rerun with explicit `--work-id`. Existing `goal.md` and its specification authority still govern scope. Establish a stream when none owns the approved work; do not overwrite an unrelated charter. Resolve ignore gates and acquire or renew the main-agent lease through [lease.md](lease.md). Worktrees share the default source tree's state; a live foreign lease blocks this write.
3. Stage the approved candidate as an absolute regular UTF-8 file with the exact approved bytes; never measure or limit the presentation. Author three separate projections under [complete-plan ownership](../references/state.md#complete-plan-reads): Goal, Requirements, Boundary, and Out of Scope in `goal.md`; Context and the complete canonical Tasks registry in `state.md`; Direction and remaining detail in root `plan.md`. Preserve charter metadata, existing task IDs, execution history, and applicable links while reconciling the approved changes. Exclude presentation-only working-directory and version-control metadata from the remainder; retain necessary workspace anchors in the charter. Do not mechanically parse headings to infer ownership. Stage each projection as a separate absolute regular UTF-8 file. Apply the [work-Markdown limit](../references/output-manifest.md) to each projection; an oversized remainder needs a revised approved plan, never truncation or automatic splitting. Bind approval to the source event or submission identity, content SHA-256, user, scope, and exceptions per [approval binding](../references/approvals.md). The hook's `fingerprint:` value hashes event content; native prompt payloads can repeat it across distinct submissions. Never pass that fingerprint as `--source`. Recover a stable identity for this actual user submission from its conversation message ID or verified transcript record position, qualified by session/transcript identity. Codex's `session_id` plus `turn_id`, a successful Claude exit's `tool_use_id`, or the adapter's message/call reference supplies an event identity directly. Redelivery retains that identity; a later approval of identical text has a different one. Do not invent random IDs, timestamps, or counters to escape a stale-event refusal. If the current submission cannot be identified, resolve that missing provenance before saving; a source-payload digest alone does not establish freshness. Under the held lease, append the approval journal event before publishing.
4. Derive `ESSENTIAL_ROOT` from this direction's installed path and run:

   ```bash
   "$ESSENTIAL_ROOT/scripts/save-approved-plan" \
     --work-id "$WORK_ID" --token "$LEASE_TOKEN" \
     --plan-file "$APPROVED_PLAN_FILE" --goal-file "$GOAL_FILE" \
     --state-file "$STATE_FILE" --remainder-file "$REMAINDER_FILE" \
     --source "$APPROVAL_SOURCE"
   ```

   The helper re-resolves centralized state, checks the lease, freezes all four inputs before writes, and writes through `state-write`. Immutable `artifacts/plan-approvals/<sha256>.txt` and `.json` retain the full approval bytes and first-approval provenance; `projections/<sha256>.txt` retains projected and prior canonical bytes. Authoritative `events/<source-sha256>.json` intents bind each approval event to the original hash, each projection's target and previous hashes, and publication revision; matching `.published.json` records verified three-file publication. Serialize calls under the main-agent lease. An unfinished event blocks newer events: retry its exact source and four inputs only when every canonical file matches its captured previous or target hash. Third-party drift requires reconciliation; never delete receipts to bypass it. A completed older event is stale even when its bytes match the latest approval. A completed latest-event retry never restores live charter or execution state. Fresh reapproval uses the new submission identity and preserves every prior event. Redelivery creates neither another plan revision nor another journal approval; reconcile any interrupted journal event instead. Historical evidence remains unchanged; this route does not migrate older streams.
5. Require `saved` or `unchanged`. Verify immutable original evidence against the returned `sha256` and all projection evidence against the returned `projections` hashes. On first publication or recovery, reread `goal_path`, `state_path`, and `plan_path` and verify all three saved hashes; the helper marks publication complete only after these checks. On a completed retry, preserve later charter and execution progress and verify its completed event instead of comparing mutable state to the old projection. Follow [complete-plan reads](../references/state.md#complete-plan-reads) before execution. A failed save, incomplete event, or evidence mismatch blocks implementation and goal creation. Reconcile revision history and execution state only after success; include returned `generated_files` in the output manifest. Revisions require explicit approval and retain prior evidence.

6. After verified persistence, discover the runtime's goal-creation capability (`create_goal` or its documented equivalent). If goal lookup exists, inspect it first. Reuse an active goal only when it requests delivery of this saved work and approved content; do not replace, complete, or relabel an unrelated goal. If an existing goal cannot be inspected or creation reports an active conflict, preserve it and continue the saved plan without another creation attempt. For a new goal, use an objective such as `Deliver the approved work at <absolute work_dir>, reading goal.md, state.md, plan.md, and applicable linked detail under the complete-plan read contract (approval SHA-256 <sha256>), including implementation and verification.` Omit token budgets unless the user specified one. Goal tools being unavailable does not block implementation from the saved plan.

Native event and approval-source evidence, adapter limits, and live verification status are recorded in the marketplace's `COMPATIBILITY.md`. Grok's normal plan UI and headless plan exit expose the same result in the investigated source, so that result never counts as approval. Its explicit submission route defers this direction until a PreToolUse denial or Stop feedback can reach the agent; a new prompt cancels any pending delivery. This bridge remains subject to the documented live-test gap.
